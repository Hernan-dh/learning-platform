01 / QA FOUNDATIONS

Quality engineering foundations

Testing is a risk-reduction activity. The useful question is not “how many tests do we have?” but “what important failure could still reach a user, and what evidence do we have that it will not?”

Foundation

Quality Assurance, software testing, SDLC, and STLC

Quality Assurance is broader than executing tests. QA improves the process that creates software: requirement review, risk analysis, testability, environments, data, automation, release controls, and feedback. Software testing evaluates a system and gathers evidence about its behavior.

SDLC (Software Development Life Cycle) is the complete lifecycle used to plan, build, verify, release, operate, and eventually retire software. A typical SDLC includes discovery or planning, requirements analysis, architecture and design, implementation, testing/verification, deployment, operation, maintenance, and retirement. The exact names and boundaries vary by organization and methodology.

STLC (Software Testing Life Cycle) is the testing-focused lifecycle inside the broader SDLC. It organizes activities such as requirement analysis, test planning and estimation, test design, environment and test-data preparation, execution, defect management, reporting, and test closure. STLC is not a competing lifecycle: it is the quality/testing perspective that runs through the SDLC.

In a sequential model these activities may appear as distinct phases; in Agile and DevOps environments they overlap continuously. QA can review requirements before code exists, developers can run unit tests during implementation, automated regression can execute in CI/CD, and monitoring can provide quality feedback after release.

Mental model: risk → expected behavior → oracle → evidence → decision.

Risk-based testing, coverage, planning, and strategy

When time is limited, prioritize by business impact, likelihood of failure, scope of change, technical complexity, detectability, and historical defects. A duplicate payment risk deserves more attention than a cosmetic spacing defect.

A test strategy defines the principles and layers used to control quality: unit, API, integration, UI, performance, security, acceptance, automation, environments, data, and release evidence. A test plan applies that strategy to a release or project with scope, owners, schedule, entry/exit criteria, and reporting.

Coverage should describe behaviors and risks, not raw test counts. A huge suite with shallow assertions can provide less assurance than a smaller suite built around critical journeys and failure modes.

Foundation

Test scenarios, test cases, and design techniques

A test scenario is a high-level behavior or journey. A test case is executable: preconditions, data, steps, expected result, and evidence. Acceptance criteria describe the business conditions that make a story complete.

Core techniques include equivalence partitioning, boundary value analysis, decision tables, and state-transition testing. Good coverage includes happy paths, negative paths, validation failures, permissions, boundaries, state changes, and recovery.

Example: login

Valid login, invalid password, locked user, expired session, missing MFA, rate limiting, safe error messages.

Example: payment

Valid payment, insufficient balance, duplicate click, retry, provider failure, rollback, reconciliation.

Foundation

Unit, integration, E2E, regression, exploratory, and acceptance testing

Unit testing validates small logic units. Integration testing verifies boundaries between components. End-to-end testing exercises a realistic journey across layers. Regression testing ensures existing behavior still works after change and can exist at any layer.

Exploratory testing combines learning, test design, and execution to discover unknown risks. Acceptance testing/UAT verifies business suitability, often with product owners or users. Push deterministic checks down to the cheapest reliable layer and keep E2E focused on critical integrated journeys.

Defect lifecycle, severity, priority, and non-reproducible bugs

A typical lifecycle is new → triaged → assigned → fixed → retested → verified → closed, with reopening when needed. Severity is technical/user impact; priority is business urgency.

For intermittent bugs, preserve build/version, environment, test data, timestamps, screenshots/video, network traces, request IDs, console/server logs, and reproduction frequency. Change one variable at a time and build hypotheses instead of repeatedly rerunning without evidence.

Traceability, reporting, and Allure

Traceability connects requirements or risks to tests, execution evidence, and defects. It answers what is covered, what failed, which requirement is affected, and what evidence exists.

A useful test report includes scope, build, environment, pass/fail/blocked status, known defects, residual risk, and a release recommendation. Allure is one reporting system that can aggregate steps, attachments, history, categories, and links. The tool matters less than stable test identity and actionable evidence.

02 / AUTOMATION ARCHITECTURE

Automation that remains maintainable

Automation is software engineering applied to quality. The goal is fast, trustworthy feedback—not a collection of scripts.

Foundation

What to automate and the test pyramid

Automate checks that are repeatable, valuable, stable enough to interpret, and executed often enough to justify maintenance. Keep human exploration for discovery, ambiguity, and one-off judgment.

Use the lowest layer that can prove the behavior. Business-rule permutations usually belong in unit or API tests; critical user journeys belong in E2E. UI checks are expensive because they cross more moving parts.

Test AutomationAutomationBrowser Automation
Intermediate → Advanced

Framework design, Page Object Model, and fixtures

A scalable framework separates test intent, domain helpers, page/API adapters, fixtures, data builders, assertions, configuration, and reporting. Avoid one giant helper file and deep inheritance trees.

Page Object Model centralizes UI interaction knowledge. Fixtures create controlled dependencies such as authenticated pages, API clients, temporary users, and cleanup. This makes failures easier to localize.

TypeScript / Page Object
export class LoginPage {
  constructor(private page: Page) {}

  async login(email: string, password: string) {
    await this.page.getByLabel('Email').fill(email);
    await this.page.getByLabel('Password').fill(password);
    await this.page.getByRole('button', { name: 'Sign in' }).click();
  }
}

Intermediate

Test data management and isolation

Prefer unique data per worker/run, API setup helpers, controlled pools with ownership, and deterministic cleanup. Shared mutable accounts are a common source of flakiness.

Protect sensitive production data: use synthetic or masked data. Test setup should be idempotent when possible so retries and reruns do not create duplicate state.

Test Data ManagementData Validation
Advanced

Flaky tests, retries, and failure diagnosis

Common causes of flakiness include timing assumptions, shared state, eventual consistency, unstable data, environment pressure, weak selectors, and uncontrolled dependencies. Distinguish product defects from flaky tests using traces, logs, network evidence, data state, and controlled repetition.

Retries are a diagnostic safety net, not a mechanism to turn failures into passes. Preserve each attempt and track tests that only pass on retry.

Intermediate

BDD, Gherkin, and Cucumber

BDD (Behavior-Driven Development) is a collaborative software-development approach that describes expected system behavior through concrete examples written from the perspective of users and business outcomes. Its purpose is to improve shared understanding between product, QA, and engineering before and during implementation.

BDD is broader than a syntax or test framework. Given / When / Then is a common structure for examples: Given establishes context, When describes an action or event, and Then describes the observable outcome. Gherkin is the structured language commonly used to write those scenarios, while Cucumber is a tool that can execute them by mapping steps to automation code.

BDD works best when examples clarify business rules and become a shared specification. It adds little value when feature files merely rewrite low-level UI actions such as “click this button” or when nobody outside the automation team reads them.

Gherkin
Feature: Transfer funds
  Scenario: Reject transfer above available balance
    Given an account with a balance of 100 USD
    When the customer attempts to transfer 150 USD
    Then the transfer is rejected
    And the balance remains 100 USD

03 / PLAYWRIGHT

Playwright deep dive

Understand the execution model—browser, context, page, locators, fixtures, projects, and evidence—rather than memorizing isolated commands.

Foundation

Browser, BrowserContext, Page, and isolation

A Browser is the browser process. A BrowserContext is an isolated session with its own cookies/storage. A Page is a tab. Playwright Test creates isolated contexts by default, preventing state leakage between tests.

Reusing one context across unrelated tests can make order matter. When authentication is expensive, reuse validated storage state, not mutable browser state.

Playwright
Browser automation and testing framework

Definition: An open-source framework for automating Chromium, Firefox, and WebKit with a modern test runner and browser-control APIs.

Main characteristics

  • BrowserContext isolation
  • Auto-waiting and actionability checks
  • Semantic locators

Foundation

Locators, semantic selection, and strictness

Prefer getByRole, getByLabel, text, and stable test IDs. They reflect user-visible semantics and survive CSS/layout changes better than deep selectors or absolute XPath.

TypeScript
const row = page.getByRole('row').filter({ hasText: 'Order #1042' });
await row.getByRole('button', { name: 'Refund' }).click();

If multiple elements match, narrow the locator using the business container or filter instead of blindly using first().

Auto-waiting and actionability

Before actions such as click(), Playwright checks that the target resolves correctly, is visible, stable, enabled where relevant, and can receive pointer events. Assertions also retry until the condition or timeout.

Avoid fixed sleeps. Wait for the state that actually matters: URL, network response, message, disabled/enabled state, or persisted data. state: 'hidden' can complete when an element is hidden or detached; opacity alone does not necessarily mean hidden.

04 / APIS & DATA

REST APIs, Postman, contracts, SQL, and data quality

A 200 response proves transport success, not business correctness. Quality at this layer includes protocol, schema, permissions, side effects, persistence, resilience, and data meaning.

Foundation

APIs, REST, HTTP methods, status codes, and authentication

API (Application Programming Interface) is a defined interface that allows one software component to communicate with another. An API specifies how a consumer can request data or behavior and what the provider promises in return. APIs can exist as web APIs over HTTP, library or operating-system interfaces, database interfaces, messaging interfaces, and other software boundaries.

For QA and automation, an API is valuable because it exposes behavior below the user interface. API tests can validate business rules, authentication and authorization, data contracts, error handling, idempotency, and integrations faster and more directly than many browser tests. API calls are also useful for creating test data and cleaning up state around UI automation.

GET reads, POST creates or triggers processing, PUT replaces a representation, and PATCH changes part of a resource. Know common 2xx, 4xx, 429, and 5xx codes, but always validate the body and resulting state.

Authentication answers “who are you?” and authorization answers “what may you do?”. Test expiry, scopes, resource ownership, role boundaries, safe errors, and session/logout behavior.

REST
Architectural style

Definition: Representational State Transfer is an architectural style for networked systems centered on resources, representations, stateless interactions, cacheability, and a uniform interface.

Main characteristics

  • Resource-oriented identifiers
  • Uses standard HTTP semantics in common web APIs
  • Stateless requests are a core constraint
  • Representations such as JSON encode resource state
  • REST is not synonymous with “any HTTP API”
QA / automation relevance: REST-aware API tests validate method semantics, status/error behavior, idempotency, caching, resource ownership, and representations.

Name / acronym: REST = Representational State Transfer.

HTTP / HTTPS
Application-layer protocol

Definition: HTTP is the Hypertext Transfer Protocol used for requests and responses on the web. HTTPS is HTTP protected by TLS encryption and server authentication (and optionally client authentication).

Main characteristics

  • Methods, status codes, headers, body, caching, content negotiation
  • Stateless request/response semantics
  • Modern versions include HTTP/2 and HTTP/3 with different transport/multiplexing behavior
  • HTTPS protects data in transit but does not make application logic secure
QA / automation relevance: API and browser tests inspect methods, status codes, headers, cookies, redirects, caching, TLS behavior, and failure mappings.

Name / acronym: HTTP = Hypertext Transfer Protocol. HTTPS is commonly read as Hypertext Transfer Protocol Secure; technically it is HTTP over TLS.

OAuth 2.0
Authorization framework

Definition: A framework for delegated authorization that allows a client to obtain scoped access to protected resources without receiving the resource owner’s password.

Main characteristics

  • Uses access tokens rather than sharing user passwords
  • Defines roles such as resource owner, client, authorization server, and resource server
  • Supports multiple grant/flow patterns for different client types
  • Scopes can restrict delegated permissions
  • Authentication is commonly added through OpenID Connect (OIDC)
QA / automation relevance: Test redirect/callback behavior, scopes, token expiry/refresh, invalid tokens, consent, client configuration, and authorization boundaries.

Name / acronym: OAuth is the framework name rather than a strict acronym. It is often informally described as “Open Authorization.”

Intermediate

JSON, JSON Schema, API contract testing, and integrations

JSON is only a representation. JSON Schema defines allowed structure, required fields, types, formats, ranges, and enums. Contract tests protect consumers from breaking producer changes.

JSON Schema
{
  "type": "object",
  "required": ["id", "status"],
  "properties": {
    "id": { "type": "string" },
    "status": { "enum": ["pending", "paid", "cancelled"] }
  }
}

Schema compatibility is not enough: business meaning can change while types remain valid. Add targeted invariants and integrated coverage.

Data-interchange format

Definition: JavaScript Object Notation is a lightweight text format for structured data using objects, arrays, strings, numbers, booleans, and null.

  • Common default format for REST APIs

JSON Schema
Schema / validation specification

Definition: A declarative vocabulary for describing and validating the structure and constraints of JSON documents.

Main characteristics

  • Defines types, required properties, enums, formats, numeric/string limits, and nested schemas
  • Supports reusable definitions and composition
  • Can forbid unexpected properties
  • Useful as an executable interface contract
QA / automation relevance: Used for API contract tests, structured LLM output validation, config validation, and detecting breaking payload changes.

Name / acronym: JSON is the acronym inside the name; “Schema” is not an acronym.

OpenAPI
API description specification

Definition: A standard machine-readable format for describing HTTP APIs, including endpoints, operations, parameters, request bodies, responses, schemas, and security schemes.

Main characteristics

  • Usually represented as YAML or JSON
  • Supports reusable schemas/components
  • Can generate documentation, clients, server stubs, and test inputs
  • Useful as a contract but still requires semantic/business assertions
QA / automation relevance: Compare implementation responses with the OpenAPI contract, detect breaking changes, generate test cases, and validate required/optional fields and error shapes.

Name / acronym: OpenAPI is a specification name, not an acronym.

GraphQL
API query language and runtime

Definition: A typed API query language and execution model in which clients select the exact fields they need from a schema.

Main characteristics

  • Strongly typed schema
  • Queries, mutations, and subscriptions
  • Nested graph-shaped selection sets
  • A single endpoint is common, unlike resource-per-URL REST conventions
  • Field-level authorization and resolver performance require careful design
QA / automation relevance: Test schema contracts, required/optional fields, authorization at nested fields, query complexity, error arrays, nullability, batching, and resolver/data consistency.

Name / acronym: GraphQL is a product/language name, not an acronym.

WebSocket
Bidirectional communication protocol

Definition: A protocol that upgrades an HTTP connection into a persistent full-duplex channel where client and server can send messages independently.

Main characteristics

  • Persistent connection
  • Bidirectional messages without request-per-message polling
  • Text and binary frames
  • Requires reconnect/heartbeat/backpressure strategies in real systems
QA / automation relevance: Test connection establishment, authentication, ordering, duplicates, reconnects, network interruption, message validation, and server cleanup.

Name / acronym: WebSocket is a protocol name, not an acronym.

Advanced

Chaining, idempotency, rate limiting, and downstream failures

Chained API tests pass explicit values from one response into the next. Idempotency is critical for retries and payments: repeated requests should not create duplicate side effects. Test duplicate clicks at UI, API, and persistent data layers.

Simulate dependency outages, latency, malformed responses, and 429/5xx behavior with controlled stubs or fault injection. Validate timeouts, retries, fallback, safe errors, and telemetry. Rate-limit tests should check threshold, headers, reset behavior, fairness, and recovery.

SQL, PostgreSQL, SQLite, MySQL, and Redis

QA commonly uses SQL to filter, join, aggregate, reconcile, and validate state. PostgreSQL and MySQL are server databases with different operational features; SQLite is embedded/file-based. Understand transactions, indexes, and concurrency at a practical level.

Redis is typically used for cache, sessions, queues, locks, and ephemeral state. When API/UI/database values disagree, stale cache or TTL behavior may be part of the problem.

SQL
SELECT customer_id, COUNT(*) AS payments
FROM payments
WHERE created_at >= CURRENT_DATE
GROUP BY customer_id
HAVING COUNT(*) > 1;

Requirements analysis and testability

Before designing tests, turn a requirement into a model of actors, preconditions, inputs, business rules, state changes, outputs, integrations, permissions, and failure behavior. The objective is not to "understand the ticket" informally; it is to expose assumptions before they become defects.

A requirement is testable when it defines observable behavior. Statements such as “the page should be fast” or “the recommendation should be relevant” need measurable criteria. Ask what the user does, what the system must do, what data is used, and what would count as failure.

Good QA contributes during refinement: identify missing edge cases, contradictory rules, hidden dependencies, unclear ownership, and requirements that cannot be verified. This is defect prevention, not just defect detection.

  • Functional questions: What inputs are accepted? What states can the entity reach? What happens on failure?
  • Data questions: Which system is the source of truth? Are fields required, unique, or time-sensitive?
  • Security questions: Which roles can perform the action? What must never be exposed?
  • Operational questions: What should be logged, monitored, retried, or recoverable?

Equivalence partitioning

Equivalence partitioning reduces redundant testing by grouping inputs expected to behave the same. Instead of testing every possible age, amount, or string length, identify classes such as valid, invalid-low, invalid-high, missing, malformed, or unauthorized.

The technique assumes that one representative value can provide confidence about the rest of the partition. That assumption should be challenged when the implementation has special cases or data-dependent rules.

  • Example: a quantity field accepts 1–99. Partitions might be <1, 1–99, and >99.
  • Also consider type/format partitions: null, empty string, non-numeric text, decimals, Unicode, or unexpected JSON types.

Selenium waits, stale elements, and ThreadLocal

An explicit Selenium wait targets a specific condition such as visibility, clickability, URL, or custom state. Broad implicit waits can make timing harder to reason about, especially when mixed with explicit waits.

Java / Selenium
private static final ThreadLocal<WebDriver> DRIVER = new ThreadLocal<>();

public static WebDriver driver() {
    return DRIVER.get();
}

@AfterEach
void cleanup() {
    if (DRIVER.get() != null) DRIVER.get().quit();
    DRIVER.remove();
}

textContent() reflects DOM text content and can include text from hidden descendants. innerText() is closer to rendered text and accounts for layout/visibility. For assertions, prefer web-first locator assertions such as toHaveText() when possible.

OOP (Object-Oriented Programming) is a programming paradigm that organizes software around objects: entities that combine state (data) with behavior (methods). Instead of treating a program only as a sequence of procedures, OOP models responsibilities and interactions between objects.

The four concepts most commonly discussed in interviews are encapsulation, abstraction, inheritance, and polymorphism. Encapsulation keeps internal state and implementation details behind a controlled public interface. Abstraction exposes the operations a caller needs without requiring knowledge of internal implementation. Inheritance allows a class to derive behavior or structure from another class. Polymorphism allows different implementations to be used through a shared interface or contract.

In test automation, these ideas appear naturally. A Page Object encapsulates selectors and UI mechanics; an API client abstracts HTTP details; an interface can allow Chromium- and Firefox-specific implementations to satisfy the same contract; and reusable components can share behavior. However, deep inheritance hierarchies often make frameworks fragile. Composition—building objects from smaller collaborators—is frequently easier to understand and maintain than a giant BaseTest class.

OOP is therefore a design tool, not a requirement to turn every concept into a class. The goal is local change, clear ownership, readable behavior, and replaceable dependencies. Java is strongly associated with OOP, but JavaScript, TypeScript, and Python also support object-oriented styles.

Core algorithm patterns for QA coding interviews

Common interview exercises are rarely about obscure algorithms; they test whether you can model data, choose an appropriate structure, reason about complexity, and handle edge cases.

Frequency maps solve counting problems; sliding windows solve many substring/range problems; two pointers handle ordered scans and cycle detection; heaps or bucket strategies solve top-K problems; sorting can remove the need for extra data structures when mutation is allowed.

Always state assumptions: empty input, duplicates, ties, Unicode/case sensitivity, whether mutation is allowed, and expected time/space complexity.

JavaScript / sliding window
function longestUnique(text) {
  let left = 0, best = 0;
  const last = new Map();
  for (let right = 0; right < text.length; right++) {
    const ch = text[right];
    if (last.has(ch) && last.get(ch) >= left) left = last.get(ch) + 1;
    last.set(ch, right);
    best = Math.max(best, right - left + 1);
  }
  return best;
}

COURSE EXPANSION / SOFTWARE FOUNDATIONS

Software systems, development models, and team collaboration

The course begins below the level of test cases: what software is, how applications are structured, how requirements evolve, which development models teams use, and how QA fits into a multi-role product organization. These foundations make later testing decisions easier to reason about.

Foundation

Software, applications, tiers, roles, and channels

Software is a set of instructions, data, and configuration that makes a computing system perform useful behavior. A software product usually includes more than executable code: interfaces, databases, integrations, configuration, infrastructure, monitoring, and operational processes all affect quality.

A single-tier application keeps interface, business logic, and data on one machine or process. A multi-tier application separates concerns—for example browser → API/service → database. Multi-tier designs introduce network latency, partial failure, authentication boundaries, caching, serialization, and version compatibility, so test strategy must cover each layer and the interactions between them.

A multi-role system gives different capabilities to users such as customer, operator, manager, and administrator. A multi-channel system exposes the same business capabilities through different channels such as web, mobile, API, kiosk, or support tools. QA should verify both channel-specific behavior and consistency of shared rules.

Single tierFewer network boundaries, but UI, logic, and storage may be tightly coupled.
Multi tierTest contracts and failure modes between frontend, services, databases, queues, and third parties.
Multi roleBuild an authorization matrix and validate positive and forbidden actions for each role.

Foundation

Manual testing workflow: scenarios, cases, execution, and status

Manual testing is deliberate human evaluation of software without relying on an automated script for every action. It is especially useful for exploration, usability, new features, visual judgment, rapidly changing areas, and scenarios where human interpretation matters.

Prioritizing and executing test scenarios

Prioritize tests by business criticality, changed code, likelihood of failure, historical defects, security/data impact, usage frequency, and cost of failure. Defect reports, evidence, triage, and lifecycle in practice

A useful defect report contains a concise title, environment/build, preconditions, exact reproduction steps, expected result, actual result, frequency, impact, severity, relevant data, and evidence. Foundation

Agile values, principles, whole-team quality, and frequent feedback

Agile is a family of approaches built around short feedback loops, collaboration, working software, adaptation, and continuous learning. It is not synonymous with Scrum, Jira, or 'no documentation.'

The Agile Manifesto emphasizes people and collaboration, usable software, customer partnership, and responsiveness to change while still valuing processes, documentation, contracts, and plans when they help. For QA, the whole-team approach means quality is considered during refinement, design, coding, automation, exploratory testing, release, and operation. Early and frequent feedback reduces the cost of misunderstanding and makes testing a continuous activity.

Twelve Agile principles — QA-oriented summary

  1. Deliver valuable software early and continuously so feedback starts soon.
  2. Expect changing requirements and adjust tests and risk analysis accordingly.
  3. Deliver working increments frequently rather than delaying validation for a large release.
  4. Business and technical people collaborate continuously; QA helps translate between them.
  5. Build around capable, trusted people and give them the environment and information needed to succeed.
  6. Use rich direct communication when ambiguity is high, while preserving decisions that need durable documentation.
  7. Working software and observable outcomes are stronger progress indicators than artifact volume.
  8. Maintain a sustainable pace; permanent crunch degrades both code and test quality.
  9. Technical excellence, testability, automation, and good design improve the ability to adapt.
  10. Prefer simplicity: avoid unnecessary work, tests, abstractions, and process.
  11. Self-organizing teams often discover better implementation and testing approaches than centrally prescribed scripts.

XML, JSON, SOAP, and REST-style web services

XML (Extensible Markup Language) represents hierarchical structured data using tagged elements and attributes. JSON (JavaScript Object Notation) represents objects, arrays, strings, numbers, booleans, and null in a compact syntax widely used by web APIs.

SOAP is a standardized XML-based messaging protocol commonly paired with WSDL contracts and enterprise web-service standards. Its historical name is Simple Object Access Protocol, although modern specifications generally treat SOAP as the protocol name. REST is an architectural style, not a wire protocol, and REST APIs commonly use HTTP plus JSON.

Do not reduce the comparison to 'SOAP is old, REST is new.' SOAP can provide strict contracts and standardized enterprise features; REST-style HTTP APIs are often simpler and more web-native. QA should validate the actual contract, authentication, namespaces/content types, errors, and business semantics.

Response time, throughput, utilization, median, percentiles, and standard deviation

Response time is the elapsed time observed for an operation. Throughput is work completed per unit of time. Utilization describes resource usage such as CPU, memory, connections, or disk. Robustness is the ability to remain correct and recover under unfavorable conditions.

The arithmetic mean is sensitive to outliers; the median is the 50th percentile. Percentiles such as p90, p95, and p99 answer 'what response time was not exceeded by this percentage of observations?' Tail percentiles are often more useful than averages for user experience.

Foundation

Test automation: benefits, limits, myths, and relationship with manual testing

Automation is not 'manual testing done by a robot.' It is software that performs repeatable checks and produces evidence. It is strongest for deterministic regression, high-volume data combinations, repeated cross-browser/API checks, CI feedback, and setup/cleanup tasks.

A useful automation decision weighs execution frequency, business risk, stability, cost to automate, cost to maintain, diagnostic value, and whether a lower-level test can prove the same behavior more cheaply.

Foundation

Black-box, white-box, and gray-box testing

Black-box testing derives tests from externally observable behavior without requiring knowledge of internal implementation. Equivalence partitions, boundary values, decision tables, state transitions, and pairwise testing are typical black-box techniques.

White-box testing uses knowledge of internal code structure or logic to design coverage, such as statements, branches, conditions, and paths. Gray-box testing informally describes testing with partial internal knowledge—for example an API tester who understands database schema and service architecture.

These approaches are complementary. Black-box tests can miss unexecuted logic; white-box coverage can execute every line while still missing incorrect requirements or missing functionality.

Statement coverage and decision/branch coverage

Statement coverage measures whether executable statements were run. Decision coverage (often called branch coverage) checks whether each decision outcome such as true and false was exercised.

100% statement coverage does not imply 100% branch coverage. A line inside an if may execute while the false path is never tested. Coverage percentages reveal what executed, not whether assertions were correct.

Useful formulas are: statement coverage = executed statements / total executable statements; decision coverage = exercised decision outcomes / total decision outcomes.

Structural coverage example
def shipping_cost(total, premium):
    if premium or total >= 100:
        return 0
    return 10

# A test with premium=True executes the 'return 0' path.
# To achieve decision coverage, also exercise a case where
# the condition evaluates False and returns 10.

Advanced

Condition coverage and MC/DC (Modified Condition/Decision Coverage)

Condition coverage checks whether each atomic boolean condition becomes both true and false. It differs from decision coverage because a compound decision can have both overall outcomes without independently exercising every condition.

MC/DC (Modified Condition/Decision Coverage) requires evidence that each condition can independently affect the overall decision outcome while other relevant conditions are held so the effect is observable. It is stricter than basic condition or decision coverage and is important in some safety-critical standards.

MC/DC test design should be systematic; brute-force testing every boolean combination gives full truth-table coverage but may be much larger than the minimal MC/DC set.

MC/DC intuition
Decision: A && (B || C)

MC/DC seeks pairs showing:
- changing A alone changes the decision,
- changing B alone changes the decision,
- changing C alone changes the decision,
while the other conditions are set so each condition's
independent effect can be observed.

Advanced

Path coverage and loop coverage

Path coverage asks whether distinct execution paths through control flow have been exercised. Complete path coverage quickly becomes infeasible because branches multiply and loops can create an unbounded number of paths.

Loop coverage focuses on meaningful iteration counts: zero iterations where possible, one iteration, typical multiple iterations, boundary counts, and values around maximum/minimum limits.

Use path/loop analysis to identify structural risk, then combine it with business-focused black-box tests. Chasing 100% path coverage is usually not practical for nontrivial programs.

Intermediate

Pairwise (all-pairs) combinatorial testing

Pairwise testing is a black-box combinatorial technique that selects a compact set of tests so every pair of parameter values appears together at least once. It is useful when many configuration dimensions make exhaustive combinations too large.

Example dimensions might be browser × operating system × locale × account role × payment method. Pairwise can dramatically reduce the matrix, but it assumes most interaction defects are caused by small combinations and does not replace risk-based tests for known three-way or higher-order interactions.

Always add explicit tests for critical combinations, boundaries, and production-heavy configurations even if a pairwise generator does not emphasize them.

PMP, CAPM, BCS, TMMi, and adjacent professional frameworks

PMP (Project Management Professional) and CAPM (Certified Associate in Project Management) are project-management credentials from PMI. They are adjacent to QA rather than testing certifications and are more useful when a role includes planning, coordination, risk, and delivery ownership.

Professional practice

A systematic debugging framework

Start with the observed fact, not a theory. Define what failed, when, for whom, and how often. Preserve the failing state and artifacts.

Localize by boundary: client/UI → network → API → service logic → database/cache → asynchronous jobs → external provider. Compare a working and failing request when possible.

Form one hypothesis at a time and choose a check that can falsify it. After finding the immediate cause, ask what allowed the defect to escape and how detection/recovery can improve.
